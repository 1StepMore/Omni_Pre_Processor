## 二、真实缺陷：守卫检查的模块名 ≠ 代码真正需要的模块名

### 现象

在 OPP 环境跑跨仓契约测试：

```
3 failed, 53 passed
FAILED tests/test_opp_ol_orf_contracts.py::TestOPPtoOLContract::test_ol_accepts_opp_source_only_format
FAILED tests/test_opp_ol_orf_contracts.py::TestOLtoORFContract::test_orf_accepts_xliff_with_target
FAILED tests/test_opp_ol_orf_contracts.py::TestFullPipelineContracts::test_full_pipeline_preserves_translations
E   ModuleNotFoundError: No module named 'ol_mcp.tools'
```

### 根因（两层，都实测）

**第一层 — 守卫太粗。**
文件 L27 写的是：

```python
pytest.importorskip("ol_mcp", reason="ol_mcp not installed (cross-module contract tests)")
```

而测试体里要的是 `from ol_mcp.tools import ...`。
`importorskip("ol_mcp")` **能通过**，`ol_mcp.tools` 却不存在 → **守卫不守，方法内硬失败**。

**第二层 — 有一个空壳目录把真包影子掉了。**
`ol_mcp.__file__ is None`、`ol_mcp.__path__ == ['.../Omni_Pre_Processor/src/ol_mcp']`：

* OPP 仓库里有个 **`src/ol_mcp/` 空目录**（**31 个文件全是 `__pycache__`，非缓存文件 0 个**，
  未跟踪、未被 ignore 规则覆盖）
* `src/` 在 `sys.path` 上 → 这个空目录被当作**命名空间包** → `import ol_mcp` 成功返回一个空包
* 所以：**即使 OL 真的装好了，这个空壳也会把它静默遮住**

⇒ 结论：**不是测试写错，是"一个空目录 + 一个粗守卫"联手把产品缺陷假象制造出来**。

### 改动

| 文件 | 改动 |
|:---|:---|
| `Omni_Pre_Processor/tests/test_opp_ol_orf_contracts.py` | 守卫改为 `pytest.importorskip("ol_mcp.tools", …)` —— 检查**代码真正需要的模块** |
| `Omni_Localizer/tests/test_new_mcp_tools.py` | 同上（`importorskip("ol_mcp")` → `importorskip("ol_mcp.tools")`） |
| `Omni_Pre_Processor/src/ol_mcp/`（空壳目录） | **删除**。走 `~/.hermes/scripts/destructive_guard.py`：先 `--selftest` 自证 → `bulk … --action delete` **dry-run 拦截** → `--apply` 执行 → 验证目录消失 |

### 验证

| 检查 | 改前 | 改后 |
|:---|:---|:---|
| `test_opp_ol_orf_contracts.py` 单跑 | **3 failed** | **1 skipped**（原因：`ol_mcp.tools not available (cross-module contract tests)`） |
| 跨仓契约 + 集成 + XLIFF 结构 | 3 failed, 53 passed | **16 passed, 1 skipped**（另一次含更多文件：33 passed, 1 skipped） |

**关键**：跳过原因是**准确**的（说清缺的是 `ol_mcp.tools`），不再伪装成产品失败。
一旦 OL 装上，这些契约测试会**真正开始跑**——这正是它们存在的意义。

**与上面 `ol_mcp` 完全同型**：

### 改动

* `tests/test_ipynb_extractor.py` · `tests/extractors/test_ipynb_level.py` → 各加一行
  `pytest.importorskip("nbformat", reason="nbformat is an optional extra (pip install '.[notebook]')")`

### 验证（两层，缺一不算）

1. **守卫生效**：未装 nbformat 时 → **7 failed 变 2 skipped**（跳过原因准确）
2. **不是拿跳过掩盖问题**：装上 `nbformat>=5.0.0` 后真跑 → **12 passed, 0 skipped**
   ⇒ 证明 **ipynb 提取器本身完全正常**，7 个红纯粹是"缺可选依赖 + 缺守卫"造成的假象

## 六、给同类的通用教训

**"测试红了"要先分清三件事，再动手：**

1. **是不是环境不对**（解释器 / 依赖没装）→ 见 `code-review-verification` 的
   `references/test-env-pitfalls.md`
2. **是不是守卫太粗**（检查的模块名 ≠ 代码真正需要的模块名 / 可选依赖没有守卫）
   → **本记录前后两轮共三次都栽在这里**
3. **才是产品缺陷**

三次"审查说缺 X"，三次核实后都不是"缺 X"：
| 审查说 | 核实后 |
|:--|:--|
| XLIFF 缺保真测试 | 测试**已存在**（`test_full_pipeline_preserves_translations`），只是**跑不起来** |
| （同上）跑不起来说明质量差 | 是**空壳目录 + 粗守卫**造成的假象 |
| — | 另加 **7 个假红**，同样源自"可选依赖缺守卫" |
| — | 再加**同型漏修 1 处**（MD 侧兄弟文件）+**守卫无效 2 处**（守自己仓的顶层包 `opp`，恒可 import） |

**结论：`importorskip` 要检查"代码真正 import 的那个模块"，不是顶层的那个名字；
更不能守"本仓自己的顶层包"—— 那恒成立，等于没守。**
